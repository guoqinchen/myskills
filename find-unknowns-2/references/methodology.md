## 核心概念提炼

### 地图 vs 地形
- **地图**：用户告诉 AI 的内容（意图、需求、假设）
- **地形**：实际的代码库、约束条件、业务规则
- **未知**：地图与地形之间的差距

### 发现未知的成本曲线
- 早期发现未知 → 低成本修正
- 中期发现未知 → 中等成本返工
- 后期发现未知 → 高成本灾难

### 10个步骤的设计逻辑
0. **挖假设** → 处理「隐式前提」的未知（问题：用户说"患者管理"但未定义"患者"范围）
1. **扫盲区** → 处理「用户知识不足」的未知
2. **展方案** → 处理「路径选择」的未知
3. **做原型** → 处理「用户偏好」的未知
4. **追问** → 处理「架构级」的未知
5. **引用** → 处理「上下文缺失」的未知
6. **计划** → 处理「多组件协调」的未知
7. **记偏差** → 处理「执行中」的未知
8. **打包** → 处理「团队对齐」的未知
9. **测验** → 处理「确认理解」的未知

> 步骤 0「挖假设」是所有步骤的前置条件。用户每一个用词都可能携带隐性前提，必须在深入任何方向前先行暴露。本步骤的设计逻辑：
> - 用户使用日常语言描述需求 → 日常语言充满歧义 → 歧义意味着假设 → 假设不成立意味着返工
> - 按「高频歧义词」统计，中文需求描述中平均每句话有 2-3 个隐含假设
> - 每个假设至少节省 1 轮返工沟通

#### 通用领域

| 用户话术 | 隐含假设 | 追问方案 |
|---|---|---|
| 「做一个**用户**管理系统」 | 用户=全员统一 | 「用户有哪些角色？管理员、普通成员、还是访客也包含？」 |
| 「用**缓存**提高性能」 | 缓存=有效方案 | 「你确认过当前瓶颈是读还是写？缓存只解决读瓶颈。」 |
| 「**一键部署**」 | 一键=不动代码 | 「一键部署需要 CI/CD 流水线，你现有的部署流程是怎样的？」 |
| 「支持**高并发**」 | 高并发=1000QPS | 「你期望的并发量级是多少？100、1000 还是 1万 QPS？」 |
| 「**费用**可以报销」 | 费用=全部覆盖 | 「费用包括哪些？云资源、第三方服务、还是人员工时也算？」 |
| 「参考**最佳实践**」 | 最佳实践=普适 | 「最佳实践通常有特定上下文，你的场景和标准 case 差异在哪？」 |

#### 数据建模领域（与当前项目相关）

| 用户话术 | 隐含假设 | 追问方案 |
|---|---|---|
| 「**患者**基本信息」 | 患者=一个人一条记录 | 「患者信息是否随时间变化？需要保留历史版本吗？患者是住院还是门诊？」 |
| 「**诊断**记录」 | 诊断=固定类别 | 「诊断是结构化编码（ICD-10）还是自由文本？允许多个诊断互斥吗？」 |
| 「**医生**和患者的关系」 | 关系=一对一 | 「一个患者可以有多个主治医生吗？医生变更时历史记录怎么处理？」 |
| 「**病历**模板」 | 模板=固定字段 | 「不同科室的病历字段差异大吗？模板可以自定义扩展字段吗？」 |
| 「**药品**目录」 | 药品=静态列表 | 「药品信息多久更新一次？通用名、商品名、厂家都算一个药品吗？」 |
| 「**权限**管理」 | 权限=角色-用户二元 | 「权限是 RBAC、ABAC 还是混合？数据级权限（医生只能看自己的患者）需要吗？」 |
| 「**统计**报表」 | 统计=当前数据 | 「统计口径需要定义吗？比如「治愈率」的计算分母是什么——所有患者还是只有出院患者？」 |
| 「**数据**导入导出」 | 数据=系统内全部 | 「导入导出的数据范围怎么限定？包含敏感字段吗？增量还是全量？」 |

|---|---|---|

### 挖假设的三层挖掘法

由浅入深，最多追问三层：

```
第一层（表面）：用户说了什么 → 他选的词有什么歧义？
  例：「做一个患者管理」→ "患者"指什么？
  
第二层（关系）：用户说的 A 和 B 是什么关系？
  例：「患者」和「医生」是一个对一个、一对多、还是多对多？

第三层（边界）：用户的方案在极端情况下是否成立？
  例：「实时同步」在 1000 患者和 1000 万患者时含义是否一样？
```

**停止条件**：用户对当前追问表示「这个我确认没问题」→ 停止这个方向，换下一个假设。

### 偏差记录完整模板

```markdown
[2026-07-16 14:30] 偏差描述
- **问题**：用户要求增加批量导入功能，原计划没有此需求
- **决策方案**：先实现基础版本（支持CSV导入），后续迭代优化高级功能
- **取舍理由**：
  - 优点：不影响核心流程上线时间
  - 缺点：高级功能（如批量更新、错误处理）延后
- **验证点**：测试批量导入100条数据的正确性和性能
- **后续跟进**：上线后收集用户反馈，评估是否需要增强

[2026-07-17 10:15] 偏差描述
- **问题**：发现数据库表结构与需求文档不一致
- **决策方案**：先按现有表结构开发，同时提交表结构变更申请
- **取舍理由**：
  - 优点：不阻塞开发进度
  - 缺点：可能需要适配两次数据结构
- **验证点**：表结构变更后验证数据迁移正确性
- **后续跟进**：协调DBA确认变更时间窗口
```

## 实施指南

### 如何判断何时触发 find-unknowns

**应该触发的信号**：
- 用户说"我没做过"、"我不知道"、"我不确定"、"我不懂"
- 需求描述模糊或不完整
- 排查问题但根因未知
- 优化任务但没有明确瓶颈
- 涉及陌生领域或代码
- 存在多个方案但无决策标准

**不应该触发的信号**：
- 用户的问题是纯知识问答（如"Python中list和tuple的区别"）
- 用户的问题是简单操作（如"帮我把JSON转成CSV"）
- 用户的问题是明确的格式转换（如"帮我格式化这段代码"）
- 用户的问题是纯计算（如"帮我计算100的阶乘"）

### 何时跳过某个步骤

| 步骤 | 跳过条件 | 跳过风险 | 后续验证点 |
|---|---|---|---|
| 挖假设 | 任务极简单（如改个变量名） | 可能遗漏关键前提 | 在追问阶段反向验证 |
| 扫盲区 | 用户明确表示熟悉该领域 | 可能遗漏隐藏盲区 | 在追问阶段确认 |
| 展方案 | 只有一个可行方案 | 可能忽略更好的选择 | 在计划阶段回顾 |
| 做原型 | 用户明确知道自己想要什么 | 可能后期发现需求偏差 | 在打包阶段验证 |
| 引用 | 用户无法提供参考物 | 可能基于错误假设 | 在测验阶段重点验证 |

### 团队协作建议

#### 代码审查时使用 find-unknowns
- 审查者可以用「扫盲区」步骤检查开发者是否遗漏了边界条件
- 审查者可以用「展方案」步骤检查是否有更好的实现方式
- 审查者可以用「测验」步骤验证开发者是否真正理解变更内容

#### 需求评审时使用 find-unknowns
- 产品经理可以用「扫盲区」步骤检查需求文档是否遗漏关键信息
- 技术负责人可以用「追问」步骤澄清架构级决策
- 团队可以用「展方案」步骤评估多个方案的可行性

## 常见误区

### 误区1：把用户描述直接当需求文档
- 用户描述往往不完整、不准确、不一致
- 需要通过追问和引用步骤验证需求的准确性

### 误区2：跳过追问直接输出方案
- 基于错误假设的方案比没有方案更糟
- 每次追问都能减少后期返工的风险

### 误区3：只给一个方案不展示取舍
- 用户需要看到全貌才能做出正确决策
- 每个方案都有优缺点，需要明确权衡

### 误区4：用模糊措辞逃避决策
- "灵活处理"、"根据情况"等措辞缺少可执行性
- 每个步骤都需要明确的操作规范和完成标志

### 误区5：不记录偏差直接继续
- 隐性假设积累导致后期难以追溯
- 每个偏差都应该记录并附带取舍理由

## 进阶技巧

### 技巧1：用问题引导用户思考
- 不要直接给答案，而是通过问题引导用户自己发现答案
- 例如："你觉得这个方案的主要风险是什么？"

### 技巧2：用示例帮助用户理解
- 抽象概念很难理解，用具体示例更容易
- 例如："比如当用户上传一个1GB的文件时，系统会怎么处理？"

### 技巧3：用对比帮助用户决策
- 单独看一个方案很难判断好坏，对比多个方案更容易
- 例如："方案A开发快但扩展性差，方案B开发慢但扩展性好，你更看重哪个？"

### 技巧4：用验证确保理解
- 不要假设用户理解了你的解释
- 例如："你能复述一下这个方案的核心思路吗？"

### 技巧5：用记录保持追溯
- 重要决策和偏差都应该记录下来
- 例如：在 `implementation-notes.md` 中记录每个关键决策
