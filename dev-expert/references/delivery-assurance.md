# 交付保障：自检 / 收尾 / 超时 / 中止（delivery-assurance）

本 reference 覆盖交付前的保障机制、失败升级后的交接与中止处理，收口于 Step 5 交付阶段。

---

## 执行率自检（SELF-AUDIT）

> 🔴 CHECKPOINT 收尾报告发出前强制执行，最多 3 轮。任一 ❌ 回退对应阶段修复 → 重走 Step 4 验证 → 重检。
> **档位剪裁**：轻量档免表检，仅一行收尾（完成度 / 产出 / 待办）；常规档豁免「架构自检 / 图谱 G1-G3 / 覆盖完整性」三行；复杂 / 大项目档跑全表（判据见 `routing.md`「档位 → 最小执行集」）。
> **证据来源归档优先**：GATE/E2E 证据在 plan `### 实测证据归档` 子区（或项目归档产物）有归档的，直接引归档行号（`[GATE-n]`/`[E2E-n]`），收尾不依赖对话流存活。
> **B池 N/A 声明抽查**：规划阶段有 `[PLAN-GATE/B池N/A]` 声明的，收尾交叉核对一行——声明未命中项与实际文件清单改动类型无冲突；无 B池声明标「无B池N/A」。
> **条件行 N/A 批量声明（减仪式开销）**：主表条件行未命中时**合并一行声明** `[SELF-AUDIT/N/A] 未命中:{行清单}——{原因一句话}`，禁逐行展开、禁静默跳过。可 N/A 行＝安全（无安全相关改动时）/ 静态兼容（无 PHP 改动时）/ 质量（无代码改动时）/ 真人功能验证（改动无 UI/后台/HTTP 入口且已按真实调用路径完成等价 E2E 时）/ 配对·跳转·防污染断言（无对称/迁移/跳转/产出物/移除类改动时）/ 前端·内联JS（无前端结构与内联 JS 改动时）/ 查册三档（动前查册·新坑即录·命中复核均未命中时）/ 自证协议（无断言·探针·复现类验证时）/ 防线·门禁·记忆（非批量且无门禁资产改动且无记忆写入触发时）。无条件必核行（交付量化/红线/GATE/Plan一致性/引用登记/完成权）不得声明 N/A。

**抗合理化触发**：本表任一项 ❌ 或出现 `## 抗合理化` 表中任一念头 → 按对应触发动作处理，不得静默降级。

**反例构造三步**（证伪行的执行方法，禁形式应付）：

1. **识别不变量**——算法依赖什么假设？（如：递归栈节点不重复、环计数不重不漏）
2. **构造违反不变量的输入**——什么输入会打破假设？
   - 空值 / null / 空集合
   - 自环 / 互环 / 平行边（图算法）
   - 并发写 / 竞态条件
   - 超大输入 / 超长字符串
   - 边界值（0 / 1 / 最大值 / 负数）
3. **验证实现是否拒绝或正确处理**——遇到反例是崩溃、错误结果、还是正确处理？

**项目知识图谱硬门禁（双保险底线；图谱属高级功能，不可用时降级为 grep 复核证据，门禁不落空）**：自校验保证"不准的边不进图"，但漏抽（动态依赖）自校验发现不了，故上述 G1/G2'/G3 为最后底线——任一不满足，SELF-AUDIT 判不通过、卡交付前。与"无验证证据=未完成"红线同源：agent 不能靠自评绕过谎报（详见 `references/project-knowledge-graph.md` 第六步）。

附加检查：裸键 grep / SQL 拼接 / 输出转义；不卡死计数 < 3；回读确认；批量修改无 SKIP/ROLLBACK；plan 中断点已标注。

**3 轮规则**：超出 3 轮 → 列出未修复项 + 原因 + 2-3 选项；下一轮人类输入到达前仍无回复 → 输出最终收尾（标未修复），不阻塞交付。

## 交付信心门控

> SELF-AUDIT 通过后、收尾报告发出前执行。按"声明 → 证据"逐条对证，禁止用感觉冒充信心。

1. **列声明**：把即将交付的关键声明拆成可验证项（需求满足 / 实现正确 / 测试通过 / 无回归 / 部署与缓存已同步 / 文档已同步）。
2. **找漏洞**：逐项自检——哪条声明最可能是假的？边界输入、失败路径、权限与路径、并发与状态、缓存与发布链路、同类文件是否会打脸？
3. **修或披露**：P0 / P1 漏洞必须先修；低风险或外部不可控项在交付里明确披露，不得隐藏。
4. **跑证据**：为每条关键声明运行对应命令或检查；改过代码跑测试 / 构建，改过 hook 跑 hook 冒烟，改过配置跑回读校验。
5. **循环判定**：关键声明未验证、或存在未缓解 P0 / P1 漏洞 → 继续处理；遇到真实外部阻塞 → 证据化交接。
6. **事实上的 100%**：含义为"当前可获得证据下，所有可运行验收均通过 + 所有已知高风险漏洞已修复 + 剩余风险已明示"，不等于绝对正确。

约束：已有证据覆盖当前制品即复用，不为每个标题重跑一套检查；不新增独立二次验收仪式；不得把局部通过说成"完成 / 修复 / 100% 有信心"。

## 穷尽后的结构化失败报告

> 触发条件：已确认失败达 L4 且 `execution-safety.md`「失败计数与升级」的 L3 7 项清单全部完成、仍未解决。与下方 Graceful Abort 分工不同——Abort = 用户中止或不可恢复阻断；本报告 = 穷尽后主动交接。

```
## 结构化失败报告
- 已验证事实：{已实测确认的事实 + 证据来源}
- 已排除可能：{已排除的假设 + 排除依据}
- 缩小后的范围：{问题确定落在哪个文件 / 函数 / 配置 / 数据流}
- 推荐下一步：{最小可行动作 + 执行命令}
- 交接信息：{精确文件:行号 + 已改动项 + 回滚方式}
```

不得把本报告写成"我不行"；它是问题边界的交接，须与「未验证项强制披露」一并进入收尾报告的待办字段。

**替代方案强制（L1）**：任何「做不到 / 不支持 / 无法」结论（不限于 L4 穷尽）须同时给出三选一——① 替代路径（换工具 / 换流程 / 外部资源）② 降级方案（本技能能覆盖的部分 + 明确限制）③ 具体待决选项（2-3 个，标推荐项）。禁只给结论不给去处；裸拒绝按未完成处理。

## 收尾报告模板（5 字段，格式刚性）

> 每次任务交付末尾强制输出，禁止自由格式。本模板为主规则「格式刚性」5 字段模板在技能侧的唯一承载；旧 one-liner 混合格式已废止。

```
## 任务收尾报告
- **任务**：{一句话，含用户原始需求}
- **完成情况**：{完成度% ＋ 状态四态之一（未验证/局部已验证/已完成/有据阻塞）＋ 量化串}
- **关键决策**：{关键决策+理由；无则「无」}
- **验证证据**：{证据编号 / 命令+输出摘要；禁只写「通过」}
- **待办**：{无遗留填「无」；有遗留注明优先级与阻塞原因；长任务/部分失败追加「部分失败明细」}
```

字段约束：

- **量化强制**：回复末输出 `(已验证主线数/总主线数)×100%`；**已验证**只计入有 Step 4 验证证据的主线项，未验证算未完成；含「局部已验证」项时注记（如 `2/3（1 项局部已验证）`）；无主线任务（信息查询/调研/演示/审查审计/无产物的日常维护）输出 `主线:N/A（元任务）`，禁虚构主线数充数
- **主线 / 支线**：仅用户核心交付物计入主线（判定见下「任务分类」）；支线标 `[优化]`/`[治理]`/`[扩展]` 前缀，不入量化串
- **完成情况**：完成度基于已验收功能 / 总功能 × 100%；禁把局部通过表述为「完成 / 100%」——「事实上的 100%」＝当前可获得证据下所有可运行验收均通过 ＋ 已知高风险已修复或已明确披露 ＋ 未篡改评分资产 ＋ 完成权归外部（用户/verifier）
- **待办·部分失败明细**：格式 `批次X失败(原因___,可resume✓/✗) | 未验证项(证据类型___/降级路径___)`；需人审项（生产动作/安全权限/门禁资产/不可回滚）须显式列「需人审：<项> + 为何需人审 + 建议动作」

**报告口径（Step 4 → Step 5）**：收尾报告只写**本回合实际观察到的结果**（工具输出 / 文件当前内容 / 页面当前状态），禁以"这一步本应产出什么"代替；失败 / 跳过 / 与预期不符 → **放报告第一句**，即使其余全部成功；提前停止 → 第一句直说并点名剩余工作，禁把部分完成写成完成；未验证就直说未验证什么、为何（禁"应该没问题"）；**范围变更由用户决定**——其余全部做完并明说漏了什么，禁静默缩窄 / 扩大 / 变换请求范围；简报先给可操作项（"构建失败：2 个鉴权用例"优于"任务完成"）。

**收尾消息写法（对外输出）**：

1. **先答后证**：先给结果再给支撑；禁先铺过程，禁开头用否定式框架。
2. **自含**：为没见过工具调用过程的读者写；依赖前文才读得懂即不合格。
3. **术语纪律**：只用对话中已建立的术语，新术语首用即定义；禁自造缩写 / 复合标签。
4. **禁对比式框架**（"是 X，不是 Y""与其…不如…"）：直接陈述目标动作或事实。
5. **空洞词清零**：delve / foster / leverage / 值得注意 / 重要的是 / 底线是。
6. **代码与数字出散文**：进代码块或表格，仅在改变读者行动时给；删减靠**省略**不靠压缩成片段；逐条罗列常规验证属噪音。
7. **内容结束就停**：不加收尾 offer、不复述已做之事。
8. **过程简报三要素**＝学到什么 / 还有什么不确定 / 下一步解决什么；禁只播报"正在做"或复述计划。
9. **收尾自检**：末段若是计划 / 分析 / 问题 / 下一步清单 / "我会…" → **现在就用工具去做**，禁因上下文长而结束回合。
10. **工具后必答**：最后一个工具调用后须用一两句陈述用户要的答案；仅"DONE/完成"式签收不算回复；禁复述调用前已写过的内容。

**交付行为纪律（对外输出的行为侧）**：

- **意图匹配**：动作请求 ⇒ 直接实现；问答/评审/解释/规划请求 ⇒ 交付物是评估，**禁夹带未请求的项目改动**（发现问题记入报告/待办，不越权动手）。
- **显式需求可见性**：用户的每条显式要求保持可见，直至完成/被用户取代/真阻塞；阻塞须明说并指名是哪条；禁悄悄丢弃、降级或替换。
- **范围即交付物**：不悄悄缩窄/扩大/变换请求范围；发现范围外问题 ⇒ 记录并报告（待办），**缩小范围是用户的决定**。
- **禁未请求的警告**：禁引入未经请求的警告、免责声明、审批流或安全合规清单（假想风险不构成理由）；真风险进收尾「待办/需人审」。
- **够用即行动**：不重推已确立的事实、不重审用户已做的决策、不叙述不会走的选项；权衡时给推荐而非穷举调查。

## 抗合理化（防自我合理化）

> 出现下列念头即停手，回到本表对应动作；「触发等级」的动作定义见 `execution-safety.md`「失败计数与升级」分级表。

### 一、收尾类（交付前自检时）

| 念头（合理化） | 现实 | 触发动作 |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | -------------------- |
| "这个改动很小，应该没问题" | 小改动也必须给验证证据 | 补验证证据 |
| "用户没提测试，就不测了" | 默认验证基线不因用户未要求而降低 | 补验证证据 |
| "这个错误不影响主流程" | 分支 / 边界错误也是未完成项，须报告 | 列入未完成项 |
| "时间不够，先这样交付" | 未完成项必须列入待办并标注阻塞原因 | 列入未完成项 |
| "我检查过了，没问题"（无证据） | 必须附命令 / 输出 / 清单证据 | 补验证证据 |
| "这个改动太小，不用规划 / 不用走 PLAN-GATE" | 是否需规划看命中定义（多文件 / 多步骤 / 多步改动），非看大小；轻量档也须最小校验 | 补 PLAN-GATE |
| "跳过或后补验证（改完即好 / 先交付后验 / 手动测过 / 应该没问题）" | 无实测证据 = 未完成；证据须当前回合实跑并见原始输出 | 补验证证据 |
| "我知道这条规则，不用再读" | 只要 1% 可能适用就须加载对应 reference | 补加载 |
| "就这一次跳过流程" | 流程无例外；跳过一次即开缺口 | 补流程 |
| "压缩摘要 / 记忆 / 旧结论里的判定已验证过，可直接引用" | 摘要与记忆仅缓存、可能过时；引用代码结论前须回实码复核 | 回实码复核 |
| "静态检查 / 纯函数断言过了，功能就正常" | 有 UI / HTTP 入口的改动必须真实驱动验证（见 `execution-safety`「真人功能验证硬约束」） | 补真人验证 |
| "这一步本应产出 X"当作已产出 | 报告须基于本回合实际观察到的结果（工具输出 / 文件现内容 / 页面现状态） | 补实测结果 |
| 把失败 / 跳过埋进结尾或并入"已完成" | 失败 / 跳过 / 与预期不符须放报告第一句 | 改写报告 |
| 悄悄缩窄 / 扩大 / 变换请求范围 | 范围变更由用户决定；其余全部做完并明说漏了什么 | 恢复原范围或显式声明 |
| 末段是"我会…"/下一步清单就结束回合 | 现在就用工具去做 | 立即执行 |

### 二、过程类（卡壳 / 推责时）

| 借口 | 判据 | 触发等级 |
| -------------------- | ------------------------------------------------ | -------- |
| "超出能力范围" | 3 种独立方案是否走完 | L1 |
| "已尝试所有方法" | 方案清单是否 < 3 种 | L2 |
| "可能是环境问题" | 是否用工具验证过（未验证的归因 = 甩锅） | L2 |
| "需要更多上下文" | 是否先查后问（有工具就先查） | L2 |
| "这不是我的范围" | 问题是否在眼前（在眼前即当前任务的 Owner） | L2 |
| "建议用户手动处理" | 是否属本任务应交付范围 | L3 |
| "差不多就行" | 约定验收项是否全过 | L3 |
| "我无法解决" | L3 的 7 项清单是否完成 | L4 |
| 把"再提交一次命令"当换了方案 | 新方案是否与上一次**本质不同** | L1 |

> 判定：凡把"懒得验证 / 无法验证 / 想快点交付 / 不该我管"包装成"合理理由"，即按对应等级动作处理；触发后按未完成项处理，如实写进收尾报告待办，不得静默降级。

## 确认超时默认规则

| 场景 | 无输入默认 |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通用（无专属约定） | 按最保守 / 安全选项推进并标 `[超时跳过]`（Agent 不阻塞等待；判定时点＝下一轮人类输入到达前） |
| 路由歧义（多路径均可） | 按已验证推荐项推进，未验证交用户 |
| 破坏性（DDL / 删**非临时**文件 / 覆盖**非临时**文件 / 批量写） | **默认取消**（保留 `.bak`，可回来重试）；**优先级高于 `execution-safety.md` 的澄清降级例外**，破坏性操作一律不降级 |
| 规划确认（建 / 改 plan 后待确认） | **保持「规划中」不自动进入修改**（父任务级 plan 须确认；同批子 plan 在父任务已授权时免逐次确认，见 `task-decomposition-and-execution.md`「批量子任务链式执行」） |
| **安全相关（涉凭证 / 权限 / 生产配置 / 不可回滚）** | **一律等待用户确认，不自动推进** |

## Graceful Abort（优雅中止）

用户主动中止或遇到不可恢复阻断时执行：

### 中止流程

1. **输出中止声明**：

   ```
   [ABORT] 中止原因: ___; 当前阶段: ___; 已完成: ___ 项
   ```

2. **保留回滚资产**：
   - 保留所有 `.bak` 及历史备份文件（最多 10 个版本）
   - \_plan.md 标注 `## 状态: 已中止`，中断点写 `阶段X / 步骤N / 中止原因`

3. **清理临时文件**：
   - 删 tests 桩 / 一次性临时脚本（不含批量脚本 `tests/s.py`）
   - **严禁删 `.bak` 及历史备份**

4. **简化收尾**（仍走 5 字段模板，禁回退旧 one-liner）：
   ```
   - 任务：{原任务}（已中止）
   - 完成情况：{完成度% ＋ 状态四态（未验证/局部已验证/有据阻塞）＋ 量化串}
   - 关键决策：{中止原因}
   - 验证证据：{已交付项的证据}
   - 待办：{未完成项 ＋ 恢复方式}
   ```

### 恢复方式

- 从 `handoff.md` 或 `_plan.md` 的 `## 中断点` 恢复
- 回滚方式：倒序逐文件 `.bak` 恢复 → `lint` 确认（`.bak` 为最新备份，数字越大越旧，最多保留 10 个版本）

## 失败重试基线

| 失败类型 | 最大重试 | 说明 |
| --------------- | -------- | ------------------ |
| 安全/数据类 | 0 | 立即升级不重试 |
| Lint/语法类 | 3 | — |
| 验证类失败 | 2 | — |
| 环境类失败 | 1 | 重试后升级 |
| 业务规则不明 | 0 | 向用户索取输入 |
| 网络/远程服务类 | 2 | 写操作前须确认幂等 |

各 reference 失败回退表如与本基线冲突，以本基线为准。

**单源收敛（防 21 处同构表膨胀）**：各子技能模板的「失败回退机制」表**只列差异项**（该技能特有的回退目标 / 上限 / 升级路径）；**共性口径（各失败类型的最大重试次数）以本节为唯一源**——模板内禁再复述基线数值、禁再写「与 SKILL.md 失败重试基线冲突时以基线为准」这类重复指针句。体检口径：接入方自建的技能体检项（如「跨文件重复行」组）应为 0 命中（同构表头与重复指针句不计）。

## 轮次与收敛

| 参数 | 默认值 |
| ---------------- | ------------------------------ |
| 默认循环轮次 | 3 |
| 安全最大轮次 | 6 |
| 每轮最大改动点数 | 3 |
| 失败熔断 | 同一Bug 2轮未修复→标记已知限制 |
| 低收益检测 | 连续2轮仅P2微调→建议提前结束 |

收敛逻辑：终极功能完成且测试通过→正常结束；无终极功能达到默认轮次且测试通过→默认结束；达到安全最大轮次→强制结束当前 Wave，输出未完成清单（长任务转交下一 Wave / 写 `handoff.md` 续做，已验证 Wave 产出物不回退清零）；连续2轮仅 P2 级→建议结束。

**轮次不分档**：轻量 / 常规 / 复杂 / 大项目共用同一轮次基线（默认 3 / 安全上限 6 / 单断点 3）。档位只决定**验证与自检深度**，不改变重试预算——轻量档禁以「改动小」为由无限重试，大项目亦禁在单 Wave 内突破 6 轮；轮次只按「单断点」计，不跨 Wave 累计。「失败熔断（同一 Bug 2 轮 → 标记已知限制）」与轮次是**两个维度**：熔断按失败签名计（同签名 2 轮即停该方向），轮次按断点预算计（3 轮）；熔断先触发时以熔断为准。

**验收项不增殖（L1）**：自检/收敛**不得新增**任务开始时未约定的验收项；禁以「随机大批量对照 / 重复跑同一测试 / 再次派人确认」制造勤奋或刷"闭环"。**工具调用次数、自检轮数与输出篇幅均不是完成度**。**例外**（唯一可追加检查的情形）：出现新的失败信号、发生实际改动、或存在任务开始时已约定但尚未覆盖的要求。禁把**局部通过**表述为「完成 / 100%」。

**终极功能判定（L1）**：当任务终极功能已完成且核心测试通过时，判定任务正常结束——**已验证的 Wave 不回退清零**（后续发现新问题开新任务修复，不影响本次交付判定）；禁止因"还能再优化"否定已完成交付。**终极功能定义**取自 plan 骨架#1「目标」第 4 要素（可验证一句话描述+有/无二值）；缺该字段时规划阶段须与用户确认一句话定义，禁止凭"大概做完了"判收敛。

## 任务分类（主线 / 支线 / 元任务）

**三轴辨析（互不替代）**：「任务分类」（本节：主线/支线归属）／「强度档位」（`agent-reasoning-patterns.md` 思维链强度分档：推理链深度）／「任务类型」（`execution-safety.md` 解题方法论：打法选择）。

| 类型 | 计入主线 | 验收标准 |
| --- | --- | --- |
| 主线（无前缀） | 是 | 明确用户价值+可独立验收 |
| 支线（[优化]/[治理]/[扩展]） | 否 | 不影响主线判定 |

**判定顺序（自上而下，取首个命中）**：

1. **元任务（N/A）**：只读或无独立产物——信息查询、调研、演示、审查审计、**无产物的日常维护**（索引重建/存档/例行巡检）。输出 `主线:N/A（元任务）`，**禁虚构主线数**充数。
2. **主线**：用户明确要求、且有独立产物并被验收的**执行类**交付物（含规则/体系整改、批量治理、脚本工具等）。
3. **支线**：其余——标注 `[优化]`/`[治理]`/`[扩展]` 前缀，落 plan 标题或文件清单备注列。

**主线判定（计入 vs 不计入）**：

| 判据 | 计入主线 | 不计入 |
| --- | --- | --- |
| 用户明确要求的核心交付物（有独立产物） | ✅ | |
| 为完成主线交付物而必需的依赖项 | ✅ | |
| 顺带修复的无关缺陷 | | ❌ |
| 纯重构 / 风格统一 / 文档补写 | | ❌ |
| 已标注 `[优化]`/`[治理]`/`[扩展]` 前缀 | | ❌ |

- **主线上限（禁增殖）**：主线总数＝任务开始时约定计入主线的条目数；实施中新增条目须**标注来源+理由并收尾披露**（用户可否决），未标注者不计入。
- **一个主线项的最小判据**：可独立验收（有明确产物或可断言的行为变化）+ 对应用户价值；二者缺一即降为支线。
- **验收证据与「已验证」口径**：证据类型＝命令+输出／测试报告／DOM断言+步骤／API响应，主线项另可用**用户确认**（第 5 类，主线特有）；每条主线项至少具备一种；**自我检验轮数与工具调用次数不构成验收证据**。`已验证` 判定（量化串分子口径）：该主线项证据齐备（≥1 类）**且**状态四态 ∈ {已完成, 局部已验证}；含「局部已验证」项时量化串须注记（如 `2/3（1 项局部已验证）`）；`未验证`/`有据阻塞` 项计入分母、不计入分子，并在收尾「待办」列出。
- **支线义务**：已完成的支线给 ≥1 条最小证据（不入量化串）；未完成的支线进收尾「待办」并明标支线。
- **归属不确定时**：无法判定是否为「用户核心交付物」的条目 ⇒ **不计入主线**，并在收尾报告「待办」列出待用户裁定。

## 状态四态标注（L1）

交付/交接时状态须落四态之一并给对应证据：

| 状态 | 判定 | 证据要求 |
| --- | --- | --- |
| `未验证` | 只有设计/计划，运行性主张尚缺证据 | 明列缺口类型（无入口/无数据/环境不可达/未实测） |
| `局部已验证` | 部分验收通过，仍有明确未完成项 | 列已过项+未过项 |
| `已完成` | **本次实际目标**的验收全部成立（不等于对未来同类任务保证成功） | 全部验收证据 |
| `有据阻塞` | 给出**已查事实 + 已排除路径 + 剩余问题 + 最小解锁动作** | 四要素齐备；禁只报"卡住了" |

禁用含糊的"差不多了/大概完成了"覆盖未完成项；长任务可叠加完成度% 但不得替代四态。

## 验收标准

| 检查维度 | 检查项 | 判定标准 |
| ---------- | -------------------------------------- | ------------------------------------------------- |
| 功能完整性 | 必选功能全部可运行 | 全部必选功能可运行 |
| 代码质量 | 无阻塞级代码问题 | 无阻塞级代码问题 |
| 构建通过 | 编译/运行成功 | 构建状态为成功 |
| 测试覆盖 | 核心路径有测试 | 核心路径有测试用例 |
| 规范符合性 | Karpathy + 项目规范 | 无规范违规 |
| 可追溯性 | 变更记录完整 | 变更文件与影响范围可查 |
| 逻辑一致性 | 需求→代码映射完整 | 需求→代码映射关系完整可追溯 |
| 长任务可靠 | 有检查点 + 未验证项/部分失败明细未隐藏 | 有 handoff/状态文件；交付含未验证项与部分失败明细 |

## 未验证项强制披露（L0）

交付中凡无法验证、降级处理或长任务部分失败的条目，必须在「已知限制/未验证项/部分失败明细」中显式列出，禁止隐藏。长任务另须附「已完成(带证据) + 未完成(下一步) + 检查点位置」。未声明证据类型的验证视为未完成（见 SKILL.md Step 4）。

四条配套硬约束：

- **缺口类型须标注**：每条未验证项注明缺口类型（无入口 / 无数据 / 环境不可达 / 未实测），不得只写「未验证」。
- **量词断言须附口径**：含「全部 / 均 / N 个 / 无残留」的断言须附枚举或全量实测口径（扫描命令 + 命中数）；无口径则降级为抽样陈述。
- **未改断言**：把「不该改的没改」写成可核验断言（如「测试文件未修改」「受保护文件逐字节一致」），禁默认省略。
- **探针与产物卫生**：临时探针 / 一次性脚本按「造 → 用 → 删 → **在原样状态重跑验收**」收尾，验收不得在探针仍在场时进行；交付物混入范围外文件 ⇒ **重新生成**而非删掉了事。
